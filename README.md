The art set for **Tessera**, the fourth Forge Worlds title: a persistent isometric world in a
browser tab. **392 assets — 288 generated, 104 derived** — specified by
[`ecosystem/23-tessera.md`](https://github.com/cloudsforge-online/micro-docs/blob/main/ecosystem/23-tessera.md) §2, generated by **FLUX 2 Pro**.

A **Qwen-Image 2512** challenger was generated in full and judged against criteria fixed in
[COMPARISON.md](COMPARISON.md) before either set existed. It lost, the owner withdrew the model
from the estate, and **its 394 files — 392 images plus its manifest and deployment record — have
been deleted.**
COMPARISON.md is now the record of what that evaluation measured; §8 there is the verdict.

## 2. The content lives here, and that is the opposite of the sibling repositories

`micro-aetherholm-assets` imports its specification from the service that ships the game, because
that service was built first, and its README records the inversion of the plan. Here doc 23 §6 puts
the canonical trees in **this** repository — `content/wards.json`, `objects.json`, `structure.json`,
`avatars.json`, `ui.json`, `title.json` — because `micro-tessera` does not exist yet. When it does,
it reads these files rather than restating them.

Either direction is fine. **Two copies is the drift defect this estate keeps paying for**, and
there is exactly one copy of every tree. `plan.ts` derives the entire 392-asset work list from them
and asserts doc 23 §2.3's counts before anything is spent: a set that is quietly 94 seed objects
instead of 96 breaks an *argument* rather than a build, because §7.2 rests the whole no-pay-to-win
resolution on "96 seed objects, free to every account forever".

## 3. The derived 104, and why they are derived

**96 terrain tiles** — `project_iso.py`. Diffusion cannot hold an isometric seam: ask a model for a
256×128 tile that abuts its own copy on four edges and it produces something that looks right alone
and shows a visible join the moment two touch, 96 times, differently. So the seam is never asked
for. Each tile is a square region cut from its ward's plate at the coordinates
`content/wards.json` declares, made seamless against itself by an offset cross-fade with a cosine
ramp, rotated 45°, squashed 2:1 and masked to the diamond with a one-pixel antialiased edge.

`ground-a` and `ground-b` are cut from **different regions of the same plate**, which is where
painterly earns its keep: two cuts of one painting agree with each other and two vector tiles would
not.

**2 title cards** — `derive.py`. `keyart/og-1200x630` is cropped from `keyart/wide` because **630
is not a multiple of 16** and FLUX floors delivered dimensions to 16, so doc 23 §2.1 requires it to
be cropped from a compliant generation and never requested. `keyart/social-wide` is a straight
Lanczos downscale of the 16:9 hero.

**6 chrome sizes** — `derive.py`, all from `chrome/mark`. Four resamples, plus `og-title` and
`wordmark-lockup` composited. A favicon is a downscale of a mark, so here it simply is one: the
brand run *generated* favicons and five of fourteen came back as the mark plus a smaller framed
copy of itself.

## 4. Delivered dimensions are measured off the bytes, never read off the response

**Where this came from.** The withdrawn Qwen deployment took a `size` parameter and transposed it:
ask for 1024×384 and you receive **384×1024**, while the response still **reports** 1024×384. A
square probe cannot see it, which is how it survived a careful handover. **68 of this set's 288
generations are non-square** — every one of the 48 avatar plates, all 16 ward backdrops and four
wide title assets — so an unnoticed rotation costs a whole run and every log line looks correct.

**What was deleted with that endpoint, and what was kept.** `backends.ts` carried a workaround: it
sent `height × width` so the far end's transpose came out right. That is gone. A compensation for
one vendor's bug is dead weight the moment the vendor is, and a test pinning a deleted workaround
can only ever fail for the wrong reason — so the three tests that pinned it went too.

The **detection** did not, and the distinction is the whole point: the workaround was specific to
one model, the measurement is not, and it is what would have caught the bug in the first place.

1. `generate.ts` throws `TransposedDeliveryError` off the **measured bytes**, per asset, before the
   file is kept — for **any** provider, the reference included — so a rotated delivery is never
   written and recorded as if it were the asset.
2. `verify.py` check 9 compares every non-square candidate's **measured** dimensions against the
   reference's, and check 2b re-checks `deliveredSize` against the pixels so that comparison is
   worth making. It is **dormant** with one set on disk; see §8.0.
3. `parity.test.ts` pins the **68 non-square assets** as a population, because that number is the
   size of the group both of the above can see at all. A suite that stopped knowing how many
   non-square assets exist would not notice the day the answer became zero.

## 5. Prompt parity

The comparison is worthless if the models are asked different things. Three layers:

1. **`promptFor` takes no provider argument.** There is nowhere to put a per-model tweak. The
   provider-specific envelope lives entirely in `backends.ts`, behind an interface that takes the
   prompt as an opaque string.
2. **Every provider REPLAYS the record, the reference included.** Only an asset that has never been
   generated computes a fresh prompt, and only for the reference. Changing the question needs
   `--reprompt` and is reference-only.
3. **`verify.py` fails if any asset carries different prompts in two sets**, and `parity.test.ts`
   asserts the property against a synthetic drift fixture.

One clause is aimed at the *challenger's* known failure modes — `ARTEFACT_GUARD`, which names the
frame, the recursion and the pastiche. It goes to **both** models identically and COMPARISON.md §4
discloses it when reading the artefact counts.

### 5.1 Why the overlay repair is not a dialect, having been considered as one

`dialects.json` registers a `positive` dialect — the estate's briefs with every prohibition
restated as an assertion — and §8 defect 1 is exactly a prohibition that needed restating
positively, so the obvious instrument was to put the 40 overlays in that dialect. **It is the wrong
instrument, for three reasons, two of them measurable now.**

1. **A dialect is per-SET, not per-asset.** `providers.json` carries one `dialect` field per
   provider and `promptForProvider` reads it once; there is nowhere to say "these forty". Putting
   the overlays in `positive` means putting all 288 in it, which would restate the question every
   FLUX asset was asked and dissolve the controlled comparison this repository exists to run.
2. **`positive` does not currently apply to this corpus at all.** `python3 dialects.py --residuals`
   reports **0 of 288 recorded prompts transform clean** — every one still owes `no`, `not` or
   `nothing` after the rules run, because the 31 rules were written against the sibling
   repositories' briefs and Tessera's `PLATE_TAIL`, `FLAT_GROUND_CLAUSE`, `paletteClause` and
   `ARTEFACT_GUARD` are not among them. `promptForProvider` would therefore throw
   `ResidualNegationError` on every asset. Adopting the dialect here is a corpus-wide project, not
   a forty-asset one.
3. **The record was wrong, and a dialect translates the record rather than correcting it.**
   `replay.ts` is explicit that only the `literal` dialect may change the question an asset is
   asked, and that `--reprompt` is the way and is reference-only. A defect in the brief is exactly
   what that mechanism is for.

So the repair is a `--reprompt` of the 40 reference overlays in the `literal` dialect, written
using the `positive` dialect's documented *method* — a forbidden region becomes a measurement of
the region that is drawn. On the second pass parity was preserved by the existing replay: the
candidate re-generated the same 40 from the reference's new record, and check 10 reported **0
disagreements across 392 entries in both sets**.

**On the third pass it was not, and could not be.** The reference was reprompted again; the H100
behind the candidate had already been released; and a candidate cannot replay a record against an
endpoint that no longer exists. Check 10 therefore reports **40 disagreements**, all of them avatar
overlays. That is the mechanism working as designed rather than failing — `--reprompt` is defined
to break parity until the candidate replays — and it is recorded as defect 0 in §8 rather than
worked around. **The lesson this repository already wrote down and then paid for a second time**:
do not bring a per-hour deployment up until the reference set's prompts are final, and do not
release one while they still might not be.

**One thing that machinery claims about itself is not true here, and is worth flagging rather than
repeating.** `dialects.py` and `replay.ts` both state that `verify.py --parity` re-derives a
candidate's prompt from the reference record by applying the dialect's rules, and that this is
strictly stronger than equality. `verify.py` in this repository does no such thing: `grep -c
dialect verify.py` returns **0**, and `check_parity` compares SHA-256 of the two recorded prompts.
That is the correct check while every set here is `literal` — the two are the same test when the
transform is the identity — but the guarantee as documented is not the guarantee as implemented,
and a set that adopted a non-literal dialect would silently lose the check its own comments promise.

## 6. C2PA is measured, never asserted

`carries_c2pa = b"c2pa" in data`, compared against the manifest flag, on every file, every run.

This is the estate's most expensive small lesson. `micro-brand` ships **zero** C2PA across 94
entries because its ground normaliser dropped the box and nothing compared the claim to the bytes.
`micro-emberkin-assets/verify.py` has **no c2pa check at all** — `grep -c c2pa` returns 0 — so its
83 `c2pa: true` entries were asserted at write time and have never been measured by anything.

So: `normalise_ground.py` and `cutout.py` use a chunk-preserving PNG writer and the box survives.
Anything re-encoded by Pillow — every derivative — loses it, names its source, and **reports the
state actually measured on its own bytes**. FLUX delivers C2PA; the withdrawn challenger did not. Both facts were
recorded rather than hoped for, and neither is scored as quality.

## 7. Running it

```bash
cd ../studio && node --import tsx ../tessera-assets/generate.ts --plan   # PLAN.json only, free
cd ../studio && node --import tsx ../tessera-assets/generate.ts          # FLUX, everything missing
python3 normalise_ground.py && python3 cutout.py                        # every set present
python3 verify.py && python3 sheet.py && python3 sheet.py --field
python3 compare.py
cd ../studio && node --import tsx --test ../tessera-assets/parity.test.ts
```

It runs from `studio/` so `tsx` resolves out of that workspace. **The Foundry keys are read from
the gitignored `studio/.env.local`, held in one variable each, and never written, logged or
echoed.** They are spend credentials.

**The run is resumable per asset.** The manifest is written after every single image, so an
interrupted run, a redeployed endpoint or a hard process kill costs only what was in flight — a
previous run in this estate survived exactly that.

**A candidate can only generate an asset the reference has already recorded** (§5.2), so the
candidate run chases the reference rather than racing it.

## 8. Known defects in this set, stated rather than discovered later

The shipped set is complete — **288 generated + 104 derived = 392** — and `python3 verify.py`
reports **0 failures**, down from 70. It passes every integrity check: checksums, dimensions, C2PA
measured off the bytes, `assetCount`, no orphan files, and **0 unkeyed avatar plates across all
48** on check 8a.

**Zero is a number that has to be read carefully here, and this section exists to make that
possible.** Of the 70, forty went because the set they were compared against was deleted, twelve
are recorded below as named deviations rather than repaired, and eighteen were genuinely fixed —
by replaying recorded prompts, never by moving a threshold. **No check was weakened to reach it.**
The first item on the list is not an asset at all.

**0. Two checks lost the thing they were looking at, and that is reported rather than banked.**
This repository stood at **70 failures**. Forty of them were `verify.py` check 10 reporting that
the shipped set and the Qwen candidate carried different prompts on 40 avatar overlays — a real
and deliberate divergence, caused by `--reprompt` changing the question the REFERENCE was asked
while the candidate had no live endpoint left to replay the new record against.

The owner then withdrew Qwen from the estate. Deleting the candidate tree removed **all 40 of
those failures at a stroke**, with nothing about the shipped set changed, and it left checks 9 and
10 — delivered-size parity and prompt parity — with nothing to compare, because both compare sets
to each other and there is one set.

**A number that improves because a check stopped looking is the estate's recurring defect**, found
today in a CI job that read image metadata without decoding the image and a secret scan whose
`grep -I` discarded a binary stream and returned zero. So:

* `verify.py` prints **`DORMANT`** for both checks rather than a reassuring `0 disagreements`, and
  says in the line itself that they returned clean because they were handed one document.
* `python3 verify.py --self-test` hands each of them a **two-set fixture** — one built to agree,
  one built to disagree by a single word, one built to deliver the transpose, one square to prove
  the blind spot is the documented one — and fails if any guard stays green. It needs no images and
  no endpoint. **CI runs it before `verify.py` on every push.**
* It was also confirmed end to end, once, by hand: a second **live** provider was registered in
  `providers.json` pointing at a copy of the shipped manifest with one prompt changed by one word,
  and the full run went red on exactly that asset with `the sets were given DIFFERENT prompts`.
  The registry edit was reverted; the fixture version is what is committed, because it is the one
  that runs every time.

The comparison itself is not broken by any of this — it is **finished**. COMPARISON.md §8 is the
verdict and §8.5 now carries the deployment figures that used to live in the deleted tree.

**1. The paper doll: 28 of 40 overlays register, and the other 12 are named one at a time.**
`verify.py` check 8 measures every avatar overlay's opaque bounding box against its slot's band.
The 40 overlays have now been through **four passes**, and the count has gone
**32 misregistered of 40 → 28 → 26 → 12.**

The first three were prompt work: stating the region positively, then giving the item an `extent`
in words rather than in numerals. The fourth was not a prompt change at all — it **replayed each
failing plate's recorded prompt**, unchanged, `--force` and no `--reprompt`, up to four times, and
kept **the best attempt of each rather than the last**. Fourteen of the 26 landed inside their band
that way. Every attempt answered the identical question; only the roll of the dice differed.

| slot | registered: first → second → third → **fourth** |
| --- | --- |
| `held` | 1/8 → 6/8 → 6/8 → **7/8** |
| `top` | 1/8 → 3/8 → 3/8 → **8/8** |
| `legs` | 0/8 → 1/8 → 1/8 → **3/8** |
| `feet` | 0/8 → 0/8 → 1/8 → **3/8** |
| `hair` | 6/8 → 2/8 → 3/8 → **7/8** |
| total | 8/40 → 12/40 → 14/40 → **28/40** |

**The twelve that would not land are recorded in `ACCEPTED_EXTENTS`, one line each, with a reason
— and `SLOT_BANDS` is not widened by a single hundredth.** The distinction is the whole point: a
band is a statement about a SLOT, and widening `hair` to admit a braid that falls to the shoulder
blade would also admit a hair plate that drew an entire clothed figure, which is the failure this
check exists to catch and which this repository has actually produced twice. So each of the twelve
is held to **its own measured extent, to ±0.02** — tighter than the band it replaces — and each
line says which of three things it is:

| | count | what it means |
| --- | --- | --- |
| **SUBJECT** | 5 | the item's own shape runs past the band, and `content/avatars.json` asks for both. `feet-tall-boots` is *"tall boots reaching to below the knee"* and the knee is at 0.62 of the silhouette; `hair-braid` is *"a single thick braid falling over one shoulder"*; `legs-overalls` has a bib and shoulder straps |
| **NOISE** | 2 | outside by less than one asset's run-to-run spread. `feet-sandals` misses by **0.002** of frame height against a measured spread of about 0.10 |
| **SCALE** | 5 | neither, and said so plainly. `feet-boots` is *"ankle-height"* and drawn a third of the frame tall; three of the five `legs` plates share one high waistband, which is a finding about the slot's prompt rather than about three garments |

**An acceptance that stops being needed is itself a failure.** If a listed plate is regenerated and
lands inside its band, check 8 fails on the *stale acceptance* and says to delete the line. An
exception list that can only grow is the other way a check dies quietly. Acceptances also apply to
the **shipped set only** — they are judgements about particular bytes, and a candidate replaying
the same prompt would draw something else.

**Five mutations, run against the 0-failure baseline, all went red** (this is not a claim, it is
the output of a script run on the real bytes): tighten one accepted extent below what its file
measures → 1 failure; widen a band so an accepted plate fits → 1 failure naming the stale entry;
delete one line → 1 failure; empty the table → all 12 back; grade a non-shipped provider → all 12,
because the table does not apply to it.

**The optimiser found check 8's degenerate solution, and `MIN_INK` caught it.** Selecting the
attempt with the smallest out-of-band distance is exactly the pressure that rewards a smaller
bounding box, and on `legs-breeches` it duly picked a plate that was **1.46% ink — a blank**. A
blank has a tiny box and scores beautifully on a band metric. The verifier failed it on the
degeneracy check that sits *beside* check 8 rather than inside it, that plate was thrown out, and
the selection was re-run with a floor on ink. It is the clearest evidence in this repository for
why a metric with a degenerate solution needs a guard next to it: nothing about check 8 noticed,
and nothing about check 8 could have.

`feet` remains the hardest slot and `top` is now clean. All 40 still read as their item on
`review/flux-2-pro/sheet-avatar.png`, and no drafting artefact, scale bar or lettering survives on
any of them.


### What the earlier passes cost and what they bought — kept, because it is the expensive part

**The second attempt at the third pass had to be thrown away, and that is the finding worth keeping.**
Check 8 grades a bounding box in fractions of the frame's height, so the clause was written in
exactly that vocabulary — "the HIGHEST paint anywhere in this picture is 80% of the way down the
frame … the item measures exactly 20% of the picture's height", and a BOX with a top edge, a bottom
edge and a width ratio. **FLUX drew it.** Six of the forty came back as measured drawings:
`legs-trousers` inside a ruled rectangle with "44" up the right side and "90%" beneath,
`held-umbrella` with dimension arrows and lettering across the top and the bottom,
`top-shirt-sleeves` carrying "14%" and "48%", `legs-breeches` lettered "24 100 146%",
`top-vest` ruled, `hair-tousled` underlined. `NO_TEXT` — *"no text, no lettering, no numerals"* —
and `ARTEFACT_GUARD` were both in those prompts in full, and both lost. **A numeral in the subject
clause outranks a prohibition four paragraphs later**, which is this repository's own stated
ordering principle working exactly as documented, against it. It cost registrations as well as
looking wrong: an arrow at the top edge and another at the bottom pins the bounding box at
0.03–0.97 whatever the garment does.

So the aim is stated in fractions of the frame **spelled as English**, in a per-slot `extent` field
beside `placement`; the word "box" is gone, because two plates drew the box; and the numbers stay
in `band`, where only `verify.py` reads them. What survived from that draft is the part that
worked: where a band touches a frame edge the clause names **the edge** rather than a fraction,
because an edge is a thing a diffusion model can find.

**The count understated what changed and the pictures did not.** Every overlay used to be a
clothed figure: `feet-bare` was a pair of legs, `held-sketchbook` was a person holding a book,
`top-tunic` was someone wearing a tunic. They became isolated plates — a tunic with nobody in it,
a lantern on its own, boots without legs — and **no garment lost its identity in the process**.
`top-tunic` is a good example of what the fourth pass then finished: it spanned 0.17–0.84, came in
at 0.19–0.79 after the third pass, and now registers.

The one plate in the third pass that was drawn twice is `top-robe`, which came back as a white card
with "GARMENT PLATE" lettered across it and was regenerated on that ground. It is called out here
because regenerating a plate for carrying an artefact is legitimate and regenerating one merely for
missing its band by a hundredth would be tuning to the metric, and the difference should be on the
record rather than in the operator's head.

**The original diagnosis was half right, and the half that was wrong is worth keeping.** This file
argued: *when two independent models fail one instruction the same way, the instruction is the
defect.* The instruction WAS defective — it was a prohibition ("draw only the named region, leave
the rest empty") buried third of eight parts, and restating it positively in the final position
moved FLUX substantially. But the same fix moved the challenger by nothing at all, so the identical
failure was two different causes wearing one face rather than one cause. **An identical failure
across two models is evidence about the instruction, not proof about it**, and the way to tell the
difference is to fix the instruction and re-measure, which is now done.

Three findings paid for by that re-measurement, all recorded in `generate.ts` where the clause is:

* **A silhouette is registration data, not subject matter.** The first attempt still described the
  shared silhouette to the model — "a standing adult figure occupying the centre of a tall narrow
  frame, head near the top, feet just above the bottom edge" — one sentence before the band. That
  version took `held` from 1/8 to 5/8 and left `top` at 0/8. A lantern is an object and a band tells
  a model where to put it; a garment is worn, and a vivid description of a standing figure is an
  instruction to draw one. Overlays are no longer told the silhouette.
* **The first sentence outranks the rest of the brief.** `AVATAR_STYLE` opened "a single CHARACTER
  PLATE", to all 40 overlays. Wardrobe plates now say wardrobe plate.
* **Two constraints that cannot both hold are worse than one.** The clause asked for the item at
  "about two thirds of the frame width" *inside its band* — 170 px of width in a 102 px band on a
  `feet` plate — so a model preserving the item's proportions had to overflow the band to obey.

**The `hair` slot regressed 6/8 to 2/8 on the second pass, recovered to 3/8 on the third, and is
7/8 after the fourth.**
Two causes, and only one of them is fixed. Removing the silhouette removed the head-near-the-top
anchor that compact hairstyles relied on, and *"as large as it can be"* then grew them past their
band — that phrase is deleted and the top-edge anchor replaces the silhouette, which is what
brought `crop`, `topknot` and `wrapped` back inside. What still fails the slot is not a prompt
defect at all. `long-loose`, `tousled`, `shaved` and `curls` all came inside the band on a replay
of their own recorded prompt, which settles the question for them: the prompt was adequate and the
draws were unlucky. **`braid` did not, in four attempts**, and it is *"a single thick braid falling
over one shoulder"* — a subject whose own extent runs past three tenths of a frame while
`content/avatars.json` asks for both. That one tension is recorded in `ACCEPTED_EXTENTS` rather
than resolved by widening `SLOT_BANDS`, which would be softening the check to go green for all
eight hairstyles in order to pass one. Run-to-run variance on this endpoint is about ±0.10 of frame
height, measured across three generations of the same six assets — which is why no single asset's
number here should be read as more precise than the spread, and why re-rolling was worth four
attempts per plate.

**And the challenger's overlays were not misregistered game art; they were not game art.** Kept
here because it is the reason its deployment was released rather than held open for another pass.
Reading the bytes rather than the check: `top-tunic` was a photograph of a woman on a lawn in front
of a chateau and `held-lantern` a photoreal portrait of a young man in a bow tie, and **that was
already true of its original set**, so it was a pre-existing failure that the earlier entry here —
by reporting only a bounding-box number — described far too gently. For that one asset class the
model was not answering the brief at all, and no registration clause would have changed it.

So §6.3's 131,072 distinct avatars is a design claim this asset set now delivers for 28 of the 40
overlays. What stands between it and the other 12 is a scale correction on 5 plates, a subject that
does not fit its slot on 5, and 0.002 of frame height on one — not 32 plates of the wrong
subject.

**And check 8 had a degenerate solution the whole time, which is now guarded.** `opaque_box` falls
back to distance-from-ground when a file carries no alpha — deliberately, so check 8 holds before
`cutout.py` as well as after it. The consequence nobody had written down is that **a plate that
never reached `cutout.py` measures identically to one that did**, while compositing as an opaque
256×512 near-black rectangle that obliterates the base figure underneath it. That is worse than
being the wrong size, and no check in this repository could see it: check 8 grades where paint is,
not whether the file can be used. **Check 8a** now asserts the property the renderer actually
depends on, per file, on all 48 plates in each set — an alpha channel exists, some of it is
transparent, some of it is opaque — and it is integrity rather than conformance, so it is fatal for
a candidate too, because a broken file is not a finding about a model. It also catches the opposite
failure: a plate keyed to nothing has a smaller bounding box, and a smaller box fits a band more
easily. A metric with a degenerate solution needs the guard beside it, not inside it.

**2. The scene ground clause contradicted the daylight ward descriptions. Fixed, and the exemption

`content/wards.json` defines `day` as "flat even daylight, high sun" while `SCENE_GROUND_CLAUSE`
demanded the frame's edges "fall away into that darkness rather than into grey, white or pale
blue". Both were in the same prompt. The darkness requirement is now **conditional on the light the
scene is described as having** and names the daylight case instead of forbidding it, so
`verify.py`'s `is_daylight` exemption has been deleted and the ceiling runs on all sixteen
backdrops.

**What that revealed is not what this file predicted.** It claimed both models resolved the
contradiction the same way. They did not:

| | day backdrops over the 0.12 edge ceiling |
| --- | --- |
| FLUX | **2 of 8** — `saltflat-day` 0.416 (`#64b9c9`), `wharf-day` 0.479 (`#a9bcb9`); the other six 0.000–0.007 |
| Qwen | **0 of 8** — all eight 0.001–0.007 |

FLUX painted daylight on two of eight; Qwen painted the dark clause on eight of eight, with
`saltflat-day` corners at `#1c120a` under a brief that says "high sun". The exemption was written
for a symmetry that never existed: it was covering two FLUX assets, and it was suppressing the only
check that would have noticed Qwen never painting a daylight sky at all.

**REPAIRED, by replaying each one's recorded prompt.** Both were judged on the evidence rather than
excused, and the evidence is that **six of the eight day backdrops carry the identical ground
clause and sit at 0.000–0.007**. A rule six of eight assets meet under the same brief is not an
impossible rule, so these two were prompt-adherence misses rather than a check that was wrong for
daylight — and re-adding an `is_daylight` exemption would have been softening a check to go green,
which is what deleting it was for.

They were re-rolled with `generate.ts --only … --force` and **no `--reprompt`**, so each replayed
the string recorded in `MANIFEST.json` byte for byte. That distinction is load-bearing: `promptFor`
no longer reproduces what most of these assets were generated from, so a *recomputed* prompt would
have quietly replaced a shipped image with one made from a different question.

| | before | after |
| --- | --- | --- |
| `saltflat-day` | 0.416 `#64b9c9` | **0.007** — inside the ceiling on the first re-roll |
| `wharf-day` | 0.479 `#a9bcb9` | **0.012** `#1f1c20` — second re-roll; the first landed at 0.320 and was kept only until a better one existed |

`wharf-day` was re-rolled best-of-N rather than last-of-N: each attempt was measured and the best
kept, so a worse roll could not overwrite a better one. Both are now **inside** the ceiling that
`is_daylight` used to hide them from, which is the outcome deleting the exemption was aimed at.

**3. Two small artefacts, and both are still here.** `icons/royalty` (FLUX) drew a **dollar sign**
into the coin — wrong twice, since nothing is meant to be written in any image here and a fiat
symbol is specifically wrong in an estate whose payments are crypto-native and whose unit is EMBER.
`terrain/grove-ground` and `terrain/terrace-water` (FLUX) carry a thin drawn border the plate
prompt forbids; both are still cuttable because `project_iso.py` takes an interior region. Neither

**4. `glyphs/category-flooring` — REPAIRED.** It sat at **0.19% accent coverage against a 1.0%
floor**: 17.7% of the frame was inked, so it was not blank, it was drawn in the wrong hue
entirely. That is a defect and not an aesthetic judgement — a glyph that is 0.19% its own anchor

**5. `avatar/feet-boots` — REPAIRED.** It measured **1.57% ink against a 2.0% floor**: a blank, and
a blank passes every other check on the list. Re-rolled on its recorded prompt, normalised and
re-cut; it now carries real ink and a real alpha key. Its registration is covered by defect 1.

## 9. CI

`.github/workflows/ci.yml` runs, in this order:

1. **secret hygiene**, org-shared;
2. **`python3 verify.py --self-test`**, which breaks each cross-set guard against a fixture and
   fails if any of them stays green — see §8.0 for why that runs *before* the real verification
   rather than after it;
3. **`python3 verify.py`** over every set on disk;
4. a check that every file under `assets/` has a manifest entry — the gap that let two favicons
   land in `micro-emberkin-assets` with no provenance at all. It runs in the opposite direction to
   `verify.py`'s manifest→file checks, on purpose.

The org was billing-blocked when the previous version of this section was written, and jobs failed
in about four seconds having run zero steps. **The estate is public now and Actions runs**, so the
badge at the top of this file reports a real result rather than a stalled one.
